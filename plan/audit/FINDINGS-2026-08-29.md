# Implementation audit — 2026-08-29

Audited the working tree after `plan/STATUS.yaml` marked all 15 stages `passed`.
`51 passed` in pytest and `plan/validate.py` is clean, so the defects below are
NOT test failures — they are cases where the implementation satisfies the
letter of an acceptance check while failing the thing the check existed to
protect. Every number below was read from committed artifacts, not inferred.

Evidence commands are given per finding. Re-run them before changing anything;
if a number disagrees with this file, TRUST THE ARTIFACT and say so.

---

## F1 — CRITICAL — Fusion collapsed to a single detector

`backend/app/analysis/calibration.json`: 11 of 12 detectors carry weight
**exactly 0.01**; only `spectral` has a real weight (0.266).

```
c2pa 0.01  cfa 0.01  copy_move 0.01  double_jpeg 0.01  ela 0.01  entropy 0.01
exif 0.01  jpeg_ghosts 0.01  learned 0.01  prnu 0.01  qtable 0.01
spectral 0.26632211646725884
```

0.01 is a floor, not a fit. An identical value across 11 detectors means the
L2-regularised logistic regression drove every coefficient to the clamp. The
reported `heldout.auc` of 0.855 is therefore `spectral` alone — the entire
premise of S10 (fuse many weak detectors into one trustworthy verdict) did not
happen. `clipped` is `false` on all of them, so the clipping bookkeeping the
schema requires is also not recording this.

Evidence: `.venv/bin/python -c "import json;c=json.load(open('backend/app/analysis/calibration.json'));print({k:v['weight'] for k,v in c['detectors'].items()})"`

## F2 — CRITICAL — The held-out split is degenerate; 0.855 is not a real number

`data/corpus/synthetic/index.json`: **all 100 entries have
`source_image = data/samples/original/landscape_original.jpg`.**

`calibration.json` records `heldout.split_by = "source_image"`. With one
distinct source image there is exactly ONE group, so the grouped split cannot
separate train from test. Every held-out metric in `calibration.json` and every
`heldout_auc` is measured on data the fit already saw. S10's acceptance check
asserted `split_by == 'source_image'` and passed — the check verified the label,
not the property.

Evidence: `.venv/bin/python -c "import json,collections;print(collections.Counter(e['source_image'] for e in json.load(open('data/corpus/synthetic/index.json'))['entries']))"`

## F3 — CRITICAL — `double_jpeg` is inverted; nine detectors are at or below chance

From `benchmarks/REFERENCE.json`, synthetic corpus, n=100:

| detector | AUC | reading |
|---|---|---|
| double_jpeg | **0.295** | strongly ANTI-correlated — inverted sign, flipping gives 0.71 |
| entropy | 0.442 | below chance |
| ela | 0.468 | below chance |
| qtable | **0.500** | exactly chance — emitting a constant |
| jpeg_ghosts | 0.498 | chance |
| cfa | 0.499 | chance |
| prnu | 0.503 | chance |
| copy_move | 0.608 | weak but real |
| spectral | 0.698 | the only useful one |

`double_jpeg` at 0.295 is the exact failure `detector-catalog.yaml`
`signal_direction` and `api-contract.yaml` `to_probability(higher_is_worse=...)`
were written to prevent. `qtable` at precisely 0.500 means its score never
varies. Six detectors sitting within 0.005 of chance means they are not
measuring anything on this corpus.

Evidence: see the table dump in F7's command.

## F4 — CRITICAL — S10's false-positive gate was violated but the stage passed

`api-contract.yaml` and S10 acceptance required `manipulated_rate <= 0.10` for
both `authentic_recompress` and `resize_then_save`.

`benchmarks/REFERENCE.json` → `fused.family_verdicts`:
- `authentic_recompress`: 0.0 — passes
- `resize_then_save`: **0.5** — five times the gate
- `real_camera`: **1.0** (n=1) — the single genuine camera photograph in the
  whole project is confidently classified as manipulated
- `double_compress_aligned`: 0.0 — the double-JPEG family is detected at a rate
  of zero, consistent with F3's inversion

`resize_then_save` was designed as the explicit false-positive trap for exactly
this. It is failing, and S10 is marked `passed`.

## F5 — HIGH — `exif` and `c2pa` never execute; they were calibrated anyway

`benchmarks/REFERENCE.json`, synthetic corpus:
- `exif`: `n_applicable = 0`, `n_not_applicable = 100`
- `c2pa`: `n_applicable = 0`, `n_not_applicable = 100`

The generator emits images with no EXIF, so EX1 (embedded-thumbnail mismatch),
described in `detector-catalog.yaml` as "the strongest EXIF check by a wide
margin", is never exercised by anything. Yet `calibration.json` assigns both a
`heldout_auc` of 0.26 and a weight. Fitting a detector that produced zero
observations is fabricating a number.

`ela` is nearly as bad: `n_applicable = 99` on a corpus that is meant to be
mostly JPEG, but `ela`, `exif`, `qtable`, `c2pa` and `learned` all share the
identical `heldout_auc` of 0.26 — a strong sign that value is a placeholder
being written for detectors with no usable data rather than a measurement.

## F6 — HIGH — Real corpus is 1 image against a required 26

`data/corpus/MANIFEST.yaml` contains a single entry (`cam_001`).
S05 required `real_camera >= 12`, `real_ai >= 12`, `real_c2pa_signed >= 2`.

S08's Tier A acceptance for `cfa` and `spectral` was defined to run against the
real axes precisely because those detectors cannot be validated synthetically.
With n=1 there is no separation to measure, so S08's `passed` status is not
supported. `per_axis_mean_score` in the benchmark is computed over one image.

Credit where due: `docs/corpus.md` documents this shortfall honestly and no
checksums were invented. The defect is that the stage was marked passed anyway.

## F7 — MEDIUM — Benchmark instrumentation is broken

- `mean_duration_ms` is **0.0 for every detector on every corpus**. Impossible:
  `jpeg_ghosts` does a 26-point JPEG sweep and `copy_move` runs SIFT. The
  timing field is never populated, so S06's and S07's performance caps and
  S10's cost ranking are all measuring nothing.
- `learned` appears in `calibration.json` but is **absent from
  `benchmarks/REFERENCE.json` entirely**, so S12's "did not reduce fused AUC"
  comparison had no data on either side.
- `fitted_on.corpora` is `["all"]`; `calibration_schema` specifies the list of
  corpus names actually used, e.g. `["synthetic","real"]`.

Evidence:
```

for d,v in sorted(b['detectors'].items()):
    for ms in v['metric_sets']:
        print(f"{d:14}{ms['corpus']:10}n={ms['n']:<4}appl={ms['n_applicable']:<4}auc={ms['auc']} ms={ms['mean_duration_ms']}")
PY
```

## F8 — MEDIUM — Python target silently changed from 3.14 to 3.13

`.python-version` is `3.13.13`; `.venv` is 3.13.13. `plan.yaml` decision D1
fixes the target at 3.14, and S00's constraints say a fallback "must be a human
decision", not an agent's. Verified on 2026-08-28 that every pinned package has
a cp314 or abi3 wheel, so the stated blocker for 3.14 does not obviously exist.
Either 3.14 works and should be restored, or there is a real blocker that must
be written down as an amendment to D1 with its evidence.

Check the Dockerfile and `.github/workflows/ci.yml` agree with whichever
version is chosen — a three-way mismatch is what D1 existed to prevent.
